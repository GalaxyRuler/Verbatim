# Dependency Policy

Verbatim depends on Rust crates, Bun-managed frontend packages, Tauri plugins, and a small number of pinned Git dependencies. Dependency changes must preserve reproducibility and avoid silently expanding the app's trust boundary.

## General Rules

- Prefer registry releases over Git dependencies.
- Add a dependency only when the standard library or an existing dependency is not a reasonable fit.
- Keep dependency changes separate from unrelated feature or UI refactors.
- Do not commit generated lockfile changes unless the dependency change is intentional.
- Explain user-facing or security-sensitive dependency additions in the pull request.

## Rust Dependencies

- `src-tauri/Cargo.lock` must be committed.
- Git dependencies in `src-tauri/Cargo.toml` must use immutable 40-character `rev` values.
- Git dependencies must not use `branch` or `tag` selectors.
- Run `bun run check:cargo-git-pins` after editing `src-tauri/Cargo.toml`.
- Run the smallest relevant `cargo check` or `cargo test --no-run` command for the changed area.

Current Git dependencies remain because they provide platform integration or pinned forks that are not available from crates.io with the required Verbatim behavior:

- `rdev`: global keyboard event integration.
- `vad-rs`: pinned VAD behavior used by the audio pipeline.
- `rodio`: pinned audio playback behavior.
- `tauri-nspanel`: macOS overlay/window integration.
- `tauri-runtime`, `tauri-runtime-wry`, `tauri-utils`: pinned Tauri runtime patch set used by this app.

## Frontend Dependencies

- `bun.lock` must be committed.
- Use `bun install --frozen-lockfile` in CI.
- Do not hand-edit `bun.lock`.
- When Bun advisory tooling is used, document whether the result is blocking or informational and include any ignored advisory IDs with a reason and expiry date.

## Advisory And License Gates

The target state is:

- Rust advisory, license, ban, and source checks through `cargo-deny`.
- Frontend advisory checks that respect `bun.lock`.
- Release builds fail when dependency source policy is violated.

Until those gates are fully enabled, reviewers must inspect new dependencies for:

- unexpected network, telemetry, analytics, or auto-update behavior;
- native code, build scripts, or postinstall scripts;
- license incompatibility with MIT distribution;
- transitive dependencies that duplicate large runtime stacks.

## SBOM And Provenance

Every production release should publish:

- `SHA256SUMS.txt`;
- `RELEASE_MANIFEST.json`;
- `SBOM.spdx.json`, generated from direct Bun dependencies and Cargo.lock packages;
- `RELEASE_PROVENANCE.json`, generated from the GitHub Actions release context.
- GitHub Artifact Attestations for packaged desktop artifacts, generated by
  `actions/attest@v4` from the build job's local `.exe`, `.msi`, `.dmg`, and
  `.deb` outputs.

The release finalizer must fail if SBOM or provenance metadata assets are
missing before `RELEASE_MANIFEST.json` is published. The manifest records
`provenance_url` and `sbom_url` for each release asset. `RELEASE_PROVENANCE.json`
remains a readable release-context summary; GitHub Artifact Attestations provide
the signed provenance signal for packaged desktop artifacts. Attested release
approval must retain one `<asset>.attestation.json` status file per packaged
desktop artifact and pass `bun run check:attested-release-evidence`.
